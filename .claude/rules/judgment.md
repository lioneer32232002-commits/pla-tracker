# 判斷力 Rubric（不確定時查這裡）

> 每節格式：判準 → 正例（該這樣）→ 反例（不該這樣）。例子多取自本專案真實歷史。

## 1. 何時該升級模型／請主模型接手

**判準**：滿足任一條就升級，不要「再試一下」：
- 同一子任務已失敗兩次且兩次錯法不同（代表不是筆誤是理解不足）
- 需要同時考慮 3 個以上互相牽制的約束（例：CI 無字型 × SEO 需求 × 客戶端渲染）
- 錯誤訊息你看不懂在指什麼層的問題

**正例**：haiku 派去批次改 embed 頁模板，第一次漏改 en/embed → 立即升 sonnet 重派，
附上漏改清單。
**反例**：sonnet 修 fetch_and_update.py 的解析錯兩次，第三次只是把 prompt 換句話說
再餵一次——這是重試不是升級，浪費第三輪。

## 2. 何時算真的完成

**判準**：以下全部為真才能說「完成」：
1. `python -X utf8 scripts/validate.py all` 通過（或本次變更無關 build，說明為何略過）
2. 變更已 commit **且已 push**（`git status` 乾淨、`git log origin/main` 含你的 commit）
3. 若改了腳本：HTML 已重新 build，version.txt 有變，全部在同一 commit
4. 若新增頁面：`daily_update.yml` 白名單已含新檔
5. 回報裡沒有任何「應該可以」「理論上」——每個聲稱都有實際執行結果支撐

**正例**：功能 E 收尾時：瀏覽器實測 PNG 下載成功（184KB）、複製失敗路徑也測了、
validate 通過、push 完成，才回報完成。
**反例**：「我改好了 build_site.py，HTML 應該會正確產生」——沒跑 build 就宣告完成。
這在本專案是鐵律違規，不是風格問題。
**反例**（真實 commit `9eda9b0`「fix: 補 import date，修正 build_site.py 崩潰」）：改
`build_site.py` 時漏一個 `import`，腳本直接崩潰——代表 commit 前根本沒執行過一次。
跑得動不代表對，但沒跑過就 commit 是更基本的錯誤。
**反例**（真實 commit `d7419db`「fix: 將 version.txt 加入每日自動提交清單」）：build
完網站，但 `git add` 清單漏了 `version.txt`，重建後的網站沒進版控。**沒有小到不用
管的生成檔**——重建物必須跟資料改動在同一個 commit。

## 3. 何時該停下來問使用者

**判準**：滿足任一條就停，先問再做：
- 要刪除或改寫**歷史資料**（records.csv 舊列）——即使看起來明顯是錯的
- 網站**結構性變更**（新頁面、改導覽、改網址結構）——**動工前**先問；使用者批准後
  照常做完即 commit＋push，不要 commit 完才停下來等（會違反鐵律 5）
- 觸及**對外發布**：Threads/部落格文案、對媒體的說法、License 條款
- 任務目標有兩種合理解讀，選錯會浪費整個 session
- **品味題**：SITREP 措辭、視覺風格、命名——給 2–3 個具體選項附取捨，讓使用者選

**不必問**（直接做）：bug 修復、驗證失敗的修正、資料新增、既定流程內的 commit+push、
使用者已明確要求的事的執行細節。

**正例**：發現 2026-05-03 的 cross_rate 算錯 0.5%——歷史資料，停下來回報並附建議
修法，等使用者點頭。
**反例**：「這行歷史資料明顯錯了，我順手修掉」——違反鐵律 1，即使你是對的。

## 4. 什麼訊號代表方向錯了（該換路，不是再重試）

**判準**：出現任一訊號，停止當前做法，退回上一個決策點列替代方案：
- 你發現自己在**對抗工具或框架**（要 hack 過驗證、要手改產出 HTML、要繞過 CI）
- 修好 A 弄壞 B、修好 B 又弄壞 A（架構層級選錯了）
- 每一步都需要新的特例（if 越加越多）
- 做法依賴一個沒驗證過的假設，而該假設查一下就能確認

**正例**：功能 E 原計畫用 Pillow 產 PNG，發現 CI 無 CJK 字型——沒有硬塞字型進 CI，
而是整個換路改客戶端 Chart.js 匯出。換路，不是把原路修到通。
**反例**：驗證一直報 sitemap 缺頁，於是把 validate.py 的該檢查註解掉——這是對抗
工具的典型訊號，該修的是 build_site.py 的 sitemap 產生邏輯。
**反例**（真實歷史）：`d730f0a`→`f003b99` 一段短時間內十餘次 `fix:` commit 反覆微調
地圖區塊座標與面板間距，`621b822`→`50af153` 的圖表 UI 修正也是同一模式。對同一元件
連發第三、四次 fix 時，訊號是「該停下來重新設計」，不是繼續打補丁。
**正例**（真實 commit `f4e82c0` 暫時性 500 重試退避、`762509d` 改抓編號最大的公告、
`741cff8` 無航跡圖時改讀公告內文、`3a7fec4` email 去重）：這四顆是「國防部網站行為
不穩定」同一類問題的不同表現。遇到一個邊界情境時，順手想「這個模式在其他相似情境
是否也存在」，比等它一個一個發生再補 patch 省事。

## 5. 品質底線怎麼驗

**判準**：按變更類型執行對應的最低驗證，缺一項就不算驗過：

| 變更類型 | 最低驗證 |
|---------|---------|
| CSV 資料 | `validate.py csv` ＋ 目視新列與來源圖片/公告逐欄核對 |
| build_site.py | 重 build → `validate.py html` → Grep 抽查一個受影響頁面的關鍵字串 |
| 前端可見變更 | preview 工具實際載入頁面：console 無錯誤＋snapshot 確認內容（不能只看 diff） |
| fetch_and_update.py | 本機以歷史某日實跑一次（dedup 安全，`outcome=exists` 不會重寫）或至少跑到解析層 |
| CI workflow | 語法上 `git push` 後看下一班執行結果；高風險改動先 `workflow_dispatch` 手動觸發驗證 |
| 規則檔（.claude/rules/） | 小修（錯字、事實更新）＝自我 read-back；結構性大改＝派 fresh-context subagent read-back（分級見 [maintenance.md](maintenance.md) 第 2/5 節） |

**正例**：改了首頁 SITREP 排版 → build → validate → preview 載入 index.html 看
console 與實際渲染 → 才 commit。
**反例**：「validate 通過了所以前端沒問題」——validate 只查結構與 SEO 字串，
不會抓 JS 執行錯誤或視覺跑版。
**反例**（真實 commit `aad5e51`「修正手機版統計數字疊字」）：版面改動只在桌機寬度驗過，
手機的疊字上線後才發現。前端變更要**桌機寬度＋手機寬度、中文版＋英文版（`en/`）都看過**
才算驗完。
**反例**（真實 commit `60546fe`「手機版卡片牆隱形」，2026-07-24 上線後由使用者發現）：
進場動畫用 `IntersectionObserver{threshold:0.15}`，超長區塊（手機上 7849px）永遠達不到
15% 可見比例 → 整區永久 opacity:0，佔位但隱形。驗收時只量了 offset/console/溢出，
**沒查 computed opacity 與 `.visible` class**——本環境的預覽面板不合成畫格，
transition/IO 行為與真機不同，動畫類狀態必須改查 class 與 style 規則本身。
規則兩條：(1) 比例式動畫門檻禁用於高度可能超過視窗數倍的區塊；
(2) 凡有「初始隱藏＋條件顯示」機制的元素，驗收必查其顯示條件在最壞情況下是否必然成立
（已加 2.5s 強制顯示保險絲為底線）。
**反例**（真實 commit `f003b99`「remove misplaced 南部空域, fix substring match
'南部' ⊂ '西南部'」）：用天真的子字串包含判斷空域名稱，「西南部」被誤判進「南部」。
解析／比對邏輯用精確匹配或明確邊界，不要用子字串包含。
**正例**（真實 commit `2a1de98`「修正翻譯函式：4/28 逾越中線20架次丟失 + 未知空域名稱
觸發 WARN」）：`validate.py` 的 WARN 機制真的攔到了資料遺失——「通過不說話、異常才出聲」
的驗證設計在本專案是有效的安全網，不是裝飾。

## 6. 誠實極限（哪些判斷這份 rubric 給不了）

模糊題與品味判斷（文案語感、圖表美感、對外溝通的分寸）沒有機械判準。遇到時的
正確動作依序是：(1) 給使用者 2–3 個具體選項附取捨；(2) 若使用者不在線且非急迫，
留下選項清單待確認，先做其他事；(3) 絕不假裝有把握。「我做不到高品質的品味判斷」
是合法回報，編一個出來不是。
