# 制度檔維護協議

> 對象：CLAUDE.md 與 `.claude/rules/*.md`。這些檔是制度本體，改壞了會讓之後
> 每個 session 變笨，所以維護有分級。

## 1. 權限分級

**可以自行改（不必問使用者）**：
- 事實過期的更新：檔案路徑變了、行數變了、CI 班次改了 → 直接改正
- 在指定區塊**追加**踩坑教訓（見第 3 節格式）
- 修錯字、修失效連結、補漏掉的指令參數

**改之前必須先問使用者（列出 before/after 差異）**：
- CLAUDE.md 的「鐵律」任何一條的增刪改
- 刪除任何規則（教訓、判準、checklist 項目）——即使你認為它過時了
- 改變檔案結構（合併/拆分/搬移規則檔、改路由表）
- 放寬任何驗證或確認要求（例：把「先問再做」改成「直接做」）

原則：**收緊規則可自行做，放寬規則要人批准。**

## 2. 改檔標準程序（每次都做）

1. 備份：`cp {檔案} .claude/backup/{檔名}.{今天日期}.bak`（backup 目錄已存在）
2. 修改
3. 自我 read-back：重讀改動段落，確認沒有跟其他規則檔矛盾
   （矛盾優先序：CLAUDE.md 鐵律 > 各規則檔）
4. Commit 訊息用 `rules:` 前綴（例：`rules: 補 OneDrive 鎖檔教訓`），照常 push
5. 若改動涉及「什麼時候讀哪個檔」→ 同步更新 CLAUDE.md 路由表

## 3. 踩坑教訓寫回哪裡、用什麼格式

判斷歸屬：
- 專案事實（檔案/CI/部署/資料）→ [project-reference.md](project-reference.md) 的「已知歷史事件」
- 環境陷阱（Windows/編碼/OneDrive/git）→ [00-diagnosis.md](00-diagnosis.md) 風險三的清單
- 判斷失誤（該問沒問、該換路沒換）→ [judgment.md](judgment.md) 對應節的正例/反例
- 派工失敗模式 → [model-dispatch.md](model-dispatch.md) 或 [delegation-templates.md](delegation-templates.md)
- 跨專案也適用的使用者偏好 → 記憶目錄（`~/.claude/projects/.../memory/`，
  記得更新 MEMORY.md 索引）

格式（一條教訓一個 bullet，三要素缺一不可）：

```
- [YYYY-MM-DD] 症狀：{觀察到什麼}。根因：{真正原因}。規則：{下次照做的一句話指令}。
```

反例（不要這樣寫）：「注意編碼問題」——沒有症狀、沒有根因、不可執行。

## 4. 膨脹控制

- **CLAUDE.md 上限 70 行**。超過＝有內容該搬去規則檔，只留路由。
- 單一規則檔超過 **250 行** → 該 session 結束前做一次精簡：合併重複、刪除已被
  更新規則取代的舊條目（刪除屬「要問使用者」級，列清單問一次批量處理）。
- 教訓累積超過 10 條時檢查：有沒有 3 條以上指向同一根因？有 → 合併成一條
  上位規則，原條目收進一行「歷史案例：…」。
- 每季（或使用者說「整理規則」時）：跑一次第 5 節的對抗審查。

## 5. 定期健檢（改動大時、或每季一次）

派一個 fresh-context subagent（模板見 [delegation-templates.md](delegation-templates.md) 模板 5），驗收條件：

```
1. 規則互相矛盾：任兩條規則在同一情境下給出不同指示 → 列出
2. 路徑/指令失效：檔案路徑、指令、工具名在當前 repo 是否真的存在（實際查證）
3. 弱模型誤讀風險：有沒有語句存在兩種合理解讀 → 列出並建議改寫
4. 路由表完整性：每個規則檔都在 CLAUDE.md 路由表中，反之亦然
```

發現的問題照第 1 節分級處理。

## 6. 備份保留

`.claude/backup/` 只保留每個檔案**最近 3 份**備份，更舊的可自行刪（git 歷史裡
都還在，備份只是為了 session 中斷時快速還原）。
