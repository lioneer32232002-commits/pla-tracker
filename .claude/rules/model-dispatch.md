# 模型調度守則

> 讀者：主對話裡的模型（任何等級）。目的：主對話的 context 是最貴的資源，
> 只放結論與決策；粗重活派給 subagent。

## 0. 本環境實際可用的東西（2026-07-04 查證）

- **Agent 工具的 subagent 類型**：`Explore`（唯讀搜索）、`general-purpose`（可改檔的
  多步任務）、`Plan`（規劃）、`claude-code-guide`（查 Claude Code/API 用法）。
- **Agent 工具的 `model` 參數**：可指定 `haiku` / `sonnet` / `opus`。不指定＝繼承主
  對話模型。（`fable` 只在 Fable session 存在，未來別指定它；若指定的型號被拒絕，
  就拿掉 model 參數用預設。）
- **Agent 工具沒有 effort 參數**——effort 只存在於 Workflow 工具內。而 **Workflow
  工具需要使用者明確要求**（說「用 workflow」或「ultracode」）才能用，平常禁用。
- 派多個互不相依的 subagent 時，**在同一則訊息裡一次全部派出**（並行）。

## 1. 指揮官不下場：什麼活必須派出去

主對話**自己做**：單檔小修改、跑 validate/build、git 操作、與使用者對話、
Grep 一兩次定位、讀 <200 行的目標區段。（這個 repo 很小，日常任務直接做，
派工反而浪費——不要為了儀式感派 subagent。）

主對話**必須派 subagent**（符合任一條）：
- 需要讀 3 個以上檔案的完整內容才能回答（→ `Explore`）
- 要在整個 repo 掃某種模式、盤點所有出現位置（→ `Explore`）
- 查網頁／查外部文件（→ `general-purpose`，開 WebSearch/WebFetch）
- 同一種修改要套用到多個檔案（→ `general-purpose`，附已驗證的範例 diff）
- 產出會很長（報告、盤點清單）——讓 subagent 落檔，只回傳路徑

**模型選擇**：機械性、有明確範例可循的活 → `haiku`；一般搜索與實作 → `sonnet`；
需要跨檔推理、除錯疑難、架構取捨 → `opus` 或不指定（繼承主模型）。

## 2. 派工三件套（缺一不可）

每個派工 prompt 必含三段（模板見 [delegation-templates.md](delegation-templates.md)）：

1. **目標與動機**：做什麼＋為什麼（動機讓 subagent 在細節上做對取捨）
2. **驗收條件**：可機械檢查的完成定義（例：「validate.py html 通過」「列出全部
   出現位置，含 檔案:行號」）
3. **回報格式**：規定只回什麼（見下面回報合約）

沒寫驗收條件的派工 prompt 不准送出。

## 3. 回報合約（subagent 必須遵守，派工時原文附上）

> 你的回報只能包含：結論（≤10 行）、關鍵證據的 檔案:行號、你改動的檔案清單、
> 未解決事項。禁止貼整段程式碼或整份檔案內容；長產物寫進檔案，回傳路徑。
> 沒把握的部分明確標「不確定」，不要編造。

## 4. 升降級路徑

- `haiku` 派工**錯一次**（驗收不過或答非所問）→ 直接升 `sonnet` 重派，不要再給
  haiku 第二次機會。
- `sonnet`／中階模型**同一子任務連錯兩次** → 升 `opus`（或主模型自己接手），
  且 prompt 必附完整失敗軌跡：兩次的 prompt、產出、驗收失敗的具體原因。
  不附失敗軌跡的升級等於重跑，會犯一樣的錯。
- **解出模式後降級**：一旦某類修改被驗證正確（例如一個檔案的改法確認可行），
  把「已驗證的範例 diff＋逐步指令」交給 `haiku`/`sonnet` 批次套用到其餘檔案。
- **同一件事最多重試兩輪**。兩輪後還不行＝方向可能錯了，停下來，照
  [judgment.md](judgment.md) 第 4 節判斷是換方法還是問使用者。

## 5. 驗證不自驗

寫的人不能當驗收的人。驗收方式按產物類型：

| 產物 | 驗收方式 |
|------|---------|
| 檔案/文件 | 派一個 **fresh-context** subagent 只給驗收條件（不給原 prompt 的做法描述），read-back 檢查內容是否達標 |
| 程式碼 | 實跑：`python -X utf8 scripts/validate.py all`＋（前端變更時）preview 工具實測；不能只靠目視 diff |
| 高風險判斷（架構取捨、資料修正方案） | 第二意見：派一個 subagent 獨立解一次，比對結論；或列 2–3 案給使用者選 |

「高風險」的定義：做錯會影響線上網站、歷史資料、或 CI 自動流程的任何決定。

## 6. 誠實極限

- subagent 體系補得了「執行品質」；補不了「品味」（文案語感、視覺、編輯取向）。
  這類題不要派工也不要硬做，直接給使用者選項。
- 不確定某工具/型號是否可用 → 實際呼叫一次小任務測試，或明說「未驗證」。
  禁止憑印象寫死型號名稱到程式或設定檔。
